Orbit is Eon's terminal-session engine: the `yazelix-orbit` server, a Rust
host with a Bend policy worker, the standalone `orbit-protocol` crate (ORBS
and ORBF), and the `orbit-governance` tool.

## Terminal authority

Orbit owns a real PTY process and the sole authoritative libghostty terminal
state. The process survives graphical-client exit or disconnection while Orbit
remains running. `ORB-C3` and `ORB-C13` bound which clients may attach and
manage a session. Attachment supplies one coherent complete host-authored
structured presentation frame followed by ordered frame revisions. The client
sends semantic input; Orbit encodes it against authoritative terminal state and
alone answers terminal queries.

Clients never reconstruct terminal authority from Formatter output or raw PTY
bytes. The presentation boundary accounts explicitly for rich terminal state,
such as styled graphemes, cursor, title, hyperlinks, and graphics resources or
capabilities, rather than becoming a plain-text grid ceiling. Persistence
across Orbit or machine restarts is outside the contract.

## Fixed boundaries

Orbit serves one terminal per session over a local Unix socket, only to the
clients `ORB-C3` and `ORB-C13` admit; multiplayer is a deliberate non-goal.
Orbit has no remote transport, Zellij compatibility, layouts, tabs, plugins, or
configuration framework. Broaden these only by explicit user decision.

Classify every `orbit-protocol` change as compatible or breaking and name each
known consumer: Venus, Eon Runtime, and Eon. Breaking changes,
adapters, and compatibility windows need an explicit user choice. A consumer
reports missing state or capability to Orbit instead of compensating for it.

## Host and worker

The Bend worker (`src/main.bend` and the policies it calls) decides every
answer. The Rust host (`src/host.rs`) and its mechanisms own the PTY,
sockets, libghostty, the event loop and cleanup, and carry out the worker's
decisions. `docs/HOST.md` owns the protocol between them, and
`src/boundary.schema` is its only definition: regenerate `src/boundary.rs`
and `src/boundary.bend` with `tools/boundary.rs` after a schema change.

Orbit has no C of its own, by the user's decision of 2026-10-17: add no C and
no custom Bend effect; the worker uses only Base's `File` effects. Read
`docs/BEND.md` before writing Bend, and add lessons there. Prefer generating
repetitive Bend over hand-writing continuation plumbing.

`LAWS.bend` holds the laws and `PROOF.bend` their proofs, which succeed with
`ALL PROOFS CHECK`; `tools/step-proof.rs` regenerates the per-fact lemmas in
`proof/`. The user owns the laws: show a new or changed law to the user before
relying on its proof. Each law gets a sensitivity check that breaks the policy
in a scratch copy and makes the proof fail.

`docs/BEHAVIOR.md` states current behavior in the present tense, and each
claim names the real-PTY check, unit test or proof that covers it, plus any
sensitivity check. Throughput runs (`tools/perf`) mean something only below a
load average of about 2; check `/proc/loadavg` first.

## Platform seam

x86_64 Linux is proved. `ORB-C14`'s native `aarch64-darwin` proof predates the
Bend host and worker, so this tree's macOS proof is a recorded gap (`EON-C7`);
Venus and Eon have not adopted macOS. Keep PTY creation, process
groups, signals, polling, file-descriptor flags, socket paths and permissions,
and platform-specific EOF or error behavior behind one narrow seam. Keep Darwin
mechanics to what `ORB-C14` requires; add no generic portability framework,
speculative trait hierarchy, second owner loop, or other platform backend.
Compilation alone is not runtime proof.

## Clean-room rule

Mars and Mars Next are behavioral references only. Do not port, copy, or adapt
their code or architecture. To reuse a piece, first state the contract it
satisfies and why a smaller implementation is insufficient, then let the user
choose.

## Contracts, crates, and test doubles

Index only user-visible behavior, correctness boundaries, ownership invariants,
and interfaces as `ORB-C*`, never functions, modules, dependencies,
configuration literals, individual tests, or speculative features.
`docs/CRATES.md` records accepted direct and architecture-shaping crate
decisions; studying a crate does not approve it.

A diagnostic client, recorded-frame corpus, or fake child process proves only
the boundary it exercises and never becomes another backend or owner. Test
clients consume the canonical wire representation, with no second handwritten
schema and no raw PTY reparsing. Mark lossy projections: a text projection
cannot prove `ORB-C6` rich-presentation fidelity.

Name Superlogical's published first product `Superlogical Rex` (`Rex` once
introduced); do not invent another name or research codename.
